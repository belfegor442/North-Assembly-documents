PURPOSE

These standards describe the basic expectations for developing and changing North Assembly software. They are intentionally practical: the point is to keep changes traceable, reviewable, and safe without turning every small change into paperwork.

1. SOURCE CONTROL

[MANDATORY]
Production source code must live in an authorized version-control repository.

[MANDATORY]
Changes must be traceable through commits, pull requests, or equivalent history. Someone reviewing a project later should be able to understand what changed and why.

[MANDATORY]
Secrets, credentials, private keys, or other sensitive values must not be committed to a repository.

2. MAKING CHANGES

[MANDATORY]
Changes should stay within the agreed scope of the task or project. If the scope needs to change, that change should be made explicit rather than quietly expanding the work.

[MANDATORY]
Security-sensitive changes must receive appropriate review before release when the team has enough capacity to provide it.

[RECOMMENDED]
Large changes should be split into pieces that can be understood and reviewed without having to reconstruct the entire project at once.

3. DEPENDENCIES

[MANDATORY]
Dependencies must be identified and used in accordance with their licenses.

[MANDATORY]
A dependency with a known and unacceptable security or licensing risk must not knowingly be introduced.

[RECOMMENDED]
When practical, keep dependency versions reproducible so that a build can be recreated later.

4. BUILDS AND RELEASES

[MANDATORY]
Development builds must be clearly distinguishable from stable releases.

[MANDATORY]
A release artifact must correspond to the source revision that was actually intended for release.

[PENDING]
Formal build environment matrix.

[PENDING]
Formal supported compiler matrix.

[PENDING]
Dependency lockfile policy.

5. DOCUMENTATION

[MANDATORY]
Important architectural or operational changes must be reflected in the relevant documentation.

[RECOMMENDED]
Documentation should explain decisions in plain language where possible. It should help the next person working on the project, not simply record that a rule exists.
