PURPOSE

This document keeps the chronological record of Monix releases and significant release states. It exists so that a released version remains traceable even after it has been replaced, recalled, deprecated, or retired.

It is a release record, not a complete technical changelog.

RELEASE IDENTIFICATION

Every release must have an identifiable version.

Possible classifications include:

* Development.
* Experimental.
* Alpha.
* Beta.
* Release Candidate.
* Stable.
* Maintenance.
* Deprecated.
* Retired.

[MANDATORY]
A release must never be intentionally represented as a different version.

RELEASE STATUS

PLANNED
The release is being considered but has not been published.

CANDIDATE
The release is being evaluated for publication.

RELEASED
The release has been published.

RECALLED
The release was withdrawn because of a significant problem.

DEPRECATED
The release remains identifiable but is no longer recommended.

RETIRED
The release is no longer supported or distributed.

FUTURE RELEASE RECORD

Each significant release should record:

VERSION
The exact version being released.

RELEASE DATE
When it was published.

RELEASE TYPE
Development, Experimental, Alpha, Beta, Release Candidate, Stable, or another approved classification.

RELEASE STATUS
Current state of the release.

BUILD IDENTIFIER
Identifier of the build artifact where applicable.

SOURCE REVISION
The source revision used to create the release.

SUMMARY
Short explanation of the release.

FEATURES
Important functionality added.

CHANGES
Important behavior or implementation changes.

FIXES
Important defects corrected.

SECURITY
Security-related changes and affected versions where relevant.

COMPATIBILITY
Supported platforms and significant compatibility changes.

KNOWN ISSUES
Important known limitations or defects.

TESTING
Tests performed, relevant results, and known failures.

RELEASE DECISION
Approval state, authority, and date.

DISTRIBUTION
Release channel, distribution location, and package identifier.

[MANDATORY]
The record must describe the version that was actually distributed.

RELEASE REQUIREMENTS

[MANDATORY]
A stable release must satisfy the applicable build, testing, security, licensing, and release requirements.

[MANDATORY]
Security-critical issues must be evaluated before publication.

[MANDATORY]
Required third-party license notices must accompany a release where applicable.

[RECOMMENDED]
Release notes should focus on changes relevant to Users.

RELEASE ARTIFACTS

Artifacts may include installers, executables, portable packages, archives, debug symbols, source packages, checksums, signatures, and release notes.

[MANDATORY]
Released artifacts must remain identifiable by version.

[RECOMMENDED]
Important artifacts should have integrity information such as checksums or digital signatures.

RELEASE CORRECTIONS

If a release contains a significant problem:

[MANDATORY]
The affected version must remain identifiable.

[MANDATORY]
The problem must be evaluated.

[MANDATORY]
A corrected release should receive a new identifiable version where appropriate.

[RECOMMENDED]
Users should be informed when a significant defect materially affects security or normal operation.

SECURITY RELEASES

Security fixes may require an accelerated release process.

[MANDATORY]
Accelerating a security release must not remove the controls necessary to establish that the fix is valid.

[RECOMMENDED]
Security release notes should identify affected versions and versions containing the fix without unnecessarily exposing sensitive implementation details.

ROLLBACK

A problematic release may be withdrawn or replaced where technically possible.

[MANDATORY]
Rollback must not erase the fact that the affected version existed.

The original version remains part of the historical record even when it is no longer distributed.

RETIREMENT

When a release becomes obsolete, its status should be updated appropriately.

[RECOMMENDED]
The reason for retirement should be recorded when known.

Possible reasons include replacement, security concerns, compatibility problems, end of support, or product retirement.

CHANGE TRACEABILITY

[MANDATORY]
Important release changes should be traceable to an identifiable source revision, change, issue, or equivalent record where technically possible.

[RECOMMENDED]
Major releases should retain their source revision, build identifier, release artifact, test evidence, and release notes.

PUBLIC RELEASE RECORDS

Public release information must contain only information intended for public disclosure.

[MANDATORY]
Release notes must not expose credentials, private infrastructure information, confidential development information, or unnecessary security-sensitive implementation details.
