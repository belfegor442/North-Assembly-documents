PURPOSE

Testing exists to provide reasonable evidence that Monix behaves as intended. It is part of normal development, not a final step performed only before release.

CORE RULES

[MANDATORY]
Tests must provide evidence relevant to the functionality being tested.

[MANDATORY]
A test that failed or did not run must never be reported as passed.

[MANDATORY]
Known critical failures must be evaluated before stable release.

[RECOMMENDED]
Tests should be deterministic and reproducible where practical.

TEST LEVELS

Monix may use:

* Unit tests.
* Integration tests.
* End-to-end tests.
* System tests.
* Regression tests.
* Performance tests.
* Security tests.
* Rendering tests.
* Compatibility tests.

UNIT TESTING

Unit tests cover isolated components such as parsers, configuration, logging, data models, detection logic, caches, utilities, and validation.

[MANDATORY]
Important components should be tested under normal and relevant failure conditions.

INTEGRATION TESTING

Integration tests verify that connected components exchange and process data correctly.

Examples include monitoring with processing, logging with storage, configuration with runtime state, shader parsing with compilation, shader compilation with caching, rendering with the application, and security analysis with events.

[MANDATORY]
Important subsystem interactions must be tested rather than assumed to work because each component works independently.

END-TO-END TESTING

End-to-end tests cover complete workflows such as startup, configuration loading, monitoring initialization, logging, shader loading, rendering initialization, settings changes, and shutdown.

[MANDATORY]
Critical User-facing workflows must be tested before stable release.

REGRESSION TESTING

Regression testing checks that a change has not broken functionality that previously worked.

[RECOMMENDED]
Major changes to rendering, shaders, monitoring, logging, security, configuration, or updates should receive regression testing.

RENDERING TESTING

Rendering tests may cover Vulkan initialization, device selection, resources, pipelines, shader compilation, multi-pass execution, feedback resources, render targets, resizing, shutdown, and recovery.

[MANDATORY]
Starting the application successfully is not enough to call a rendering test successful. The relevant rendering operation must actually be validated.

SHADER TESTING

Shader testing may cover parsing, presets, includes, dependencies, compilation, SPIR-V, reflection, pipeline creation, runtime execution, multi-pass behavior, feedback, and cache interaction.

[MANDATORY]
Invalid shaders must produce an appropriate failure result.

[MANDATORY]
Shader compilation failures must never be reported as successful compilation.

SHADER CACHE TESTING

The cache should be tested for hits, misses, invalidation, dependency changes, compiler changes, corruption, manifest errors, atomic writes, and eviction.

[MANDATORY]
Stale cache data must not be used when relevant source, dependency, compiler, or compatibility information has changed.

MONITORING TESTING

Monitoring tests may cover CPU, memory, GPU, temperature, storage, network, and process information.

[MANDATORY]
Unavailable hardware data must be handled safely and must not be replaced with invented values.

PROCESS TESTING

Process analysis may be tested for discovery, metadata, resource measurements, classification, reputation, and heuristic analysis.

[MANDATORY]
Heuristic classifications must remain distinguishable from verified facts.

SECURITY TESTING

Security tests may cover authentication, authorization, access control, secret handling, input validation, update verification, security logging, privileged operations, process actions, and configuration security.

[MANDATORY]
Security-critical functionality must be tested before stable release.

[MANDATORY]
Testing must not use uncontrolled real-world targets without appropriate authorization.

SCRAM TESTING

SCRAM requires separate consideration of TEST and REAL behavior.

[MANDATORY]
TEST mode must validate logic without intentionally executing actions reserved for real emergency operation.

[MANDATORY]
REAL-mode testing may only occur when the environment, permissions, and consequences are properly controlled.

[MANDATORY]
The active mode must be verified before any high-impact action.

CONFIGURATION TESTING

Configuration tests may cover valid and invalid values, missing values, defaults, corruption, migration, and runtime changes.

[MANDATORY]
Invalid configuration must not silently create unsafe or undefined behavior.

LOGGING TESTING

Logging tests may cover event creation, severity, formatting, timestamps, source information, buffers, persistence, rotation, and failure handling.

[MANDATORY]
Tests must verify that credentials and other secrets are not unintentionally written to logs.

SNAPSHOT TESTING

Snapshot tests may cover capture, serialization, storage, loading, validation, corruption, compatibility, migration, import, export, and restoration.

[MANDATORY]
Corrupted or incompatible snapshots must not be silently accepted as valid.

PERFORMANCE TESTING

Performance tests may measure CPU, memory, GPU, startup, rendering, shader compilation, cache behavior, logging, and monitoring overhead.

[RECOMMENDED]
Representative workloads should be used.

[MANDATORY]
A performance improvement must not be accepted when it introduces an unacceptable correctness or security regression.

COMPATIBILITY TESTING

Compatibility may cover operating-system versions, hardware, GPU vendors, graphics drivers, displays, storage, and other supported configurations.

[PENDING]
Official compatibility matrix.

FAILURE TESTING

Monix should be tested under controlled failures such as missing files, invalid configuration, corrupted cache, shader compilation errors, GPU initialization failure, unsupported hardware, missing sensors, network failures, permission denial, and unexpected process termination.

[MANDATORY]
Expected failures must be handled without falsely reporting successful operation.

TEST DATA

[MANDATORY]
Test data must be appropriate for the test being performed.

[MANDATORY]
Production secrets and unnecessary real personal data must not be used in testing.

[RECOMMENDED]
Synthetic or controlled test data should be preferred.

TEST ENVIRONMENTS

Testing may occur in development, dedicated test environments, staging, or controlled production validation where necessary.

[MANDATORY]
Tests capable of modifying real data or production systems require appropriate authorization and controls.

TEST RESULTS

PASS — expected behavior confirmed.

FAIL — expected behavior not confirmed.

BLOCKED — testing could not be completed because of an external condition.

SKIPPED — testing was intentionally not executed.

NOT APPLICABLE — the test does not apply to the tested configuration.

[MANDATORY]
Anything that was not executed must not be represented as PASS.

DEFECT SEVERITY

CRITICAL — severe security, data-integrity, essential-functionality, or stability impact.

HIGH — major functional or operational impact.

MEDIUM — meaningful issue without normally preventing general use.

LOW — limited-impact issue.

[MANDATORY]
Severity must reflect the actual or reasonably assessed impact.

RELEASE BLOCKERS

A defect may block a release when it creates a critical security problem, serious data corruption, loss of essential functionality, repeatable catastrophic failure, or violation of a mandatory release requirement.

[MANDATORY]
Known release blockers must be evaluated before stable release.

[MANDATORY]
Release blockers must not be deliberately hidden from the release decision process.

TEST EVIDENCE

[RECOMMENDED]
Important test runs should retain the test name, version, environment, result, date, relevant logs, failure information, and associated build or change.

[MANDATORY]
Evidence must not be altered to manufacture a false result.

AUTOMATED TESTING

[RECOMMENDED]
Automated build validation, unit tests, integration tests, shader tests, security checks, and regression tests should be used where practical.

RELEASE TEST GATE

Before a stable release:

[MANDATORY]
There must be a successful build, required tests must have been executed, critical failures must have been evaluated, and applicable security and compatibility checks must be complete.

[MANDATORY]
A failed mandatory gate must be resolved, formally accepted by the appropriate authority, or prevent the release.
