PURPOSE

This document describes how Monix moves from source code to a tested release. It covers source state, configuration, compilation, shaders, validation, packaging, approval, distribution, updates, and rollback.

The goal is simple: a release should be identifiable, testable, and appropriate for the channel in which it is distributed.

BUILD RULES

[MANDATORY]
A release build must come from an identifiable source revision or equivalent controlled state.

[MANDATORY]
A failed build must never be presented as successful.

[MANDATORY]
Required validation must be completed before a build is considered releasable.

[RECOMMENDED]
Builds should be automated where practical.

BUILD CONFIGURATIONS

Monix may use configurations such as:

* Debug.
* Development.
* Testing.
* Release.

[MANDATORY]
Development-only functionality must not unintentionally remain active in a stable release when it creates a security, stability, or information-disclosure risk.

SOURCE AND DEPENDENCIES

[MANDATORY]
The source revision used for a release must be identifiable.

[MANDATORY]
The intended dependency state must be controlled sufficiently to avoid accidental changes between builds.

[MANDATORY]
Third-party dependencies must comply with their applicable licenses.

TOOLCHAIN

The Monix build may use C++, CMake, the Vulkan SDK, Slang tooling, platform SDKs, linkers, and packaging tools.

CLEAN BUILD

A clean build removes generated artifacts from previous builds before compiling the intended source state.

[MANDATORY]
A release must not accidentally depend on stale generated files from an unrelated source state.

COMPILATION

The normal build path is:

SOURCE
-> CONFIGURE
-> GENERATE
-> COMPILE
-> LINK
-> POST-BUILD VALIDATION

[MANDATORY]
Compilation or linking errors must fail the corresponding build stage.

[MANDATORY]
The resulting executable must correspond to the intended configuration and source state.

SHADER BUILD

Where shaders are part of the release:

[MANDATORY]
Required shaders, presets, includes, and dependencies must be available and valid.

[MANDATORY]
Shader compilation failures must fail the applicable validation stage.

[MANDATORY]
A failed shader build must never be represented as successful initialization or release validation.

BUILD VALIDATION

A successful compiler exit code is not enough to declare a build valid.

Validation may cover:

* Executables.
* Version information.
* Required libraries.
* Runtime resources.
* Shader resources.
* Configuration.
* Package contents.
* Architecture compatibility.
* Security-sensitive content.

TESTING

Applicable release testing may include:

* Unit tests.
* Integration tests.
* End-to-end tests.
* Rendering tests.
* Shader tests.
* Security tests.
* Performance tests.
* Compatibility tests.
* Regression tests.

[MANDATORY]
Required release tests must be executed before a stable release.

[MANDATORY]
Skipped or unavailable tests must not be reported as passed.

RELEASE ARTIFACTS

Artifacts may include executables, libraries, shader resources, configuration files, installers, archives, debug symbols, checksums, and signatures.

[MANDATORY]
Release artifacts must be identifiable by product version and build state.

[MANDATORY]
Release packages must not intentionally contain secrets or unrelated development artifacts.

[MANDATORY]
Required third-party license notices must be included.

PACKAGE VALIDATION

Before distribution, the package should be checked for:

* Correct files.
* Correct version.
* Required dependencies.
* Resource paths.
* Expected runtime behavior.
* License requirements.
* Security-sensitive material.

INSTALLATION AND UPDATE TESTING

Where applicable, releases should be tested for fresh installation, upgrade, reinstallation, uninstallation, configuration preservation, dependency failures, and automatic updates.

[MANDATORY]
Automatic updates must be tested for valid packages, invalid packages, interrupted updates, failed verification, version transitions, and rollback where supported.

RELEASE CHANNELS

Monix may use:

* Development.
* Experimental.
* Alpha.
* Beta.
* Release Candidate.
* Stable.

[MANDATORY]
The release channel must accurately describe the maturity of the build.

RELEASE APPROVAL

A stable release requires the applicable build, test, security, package, and approval requirements to be satisfied.

RELEASE GATE

SOURCE
-> BUILD
-> VALIDATION
-> TESTING
-> SECURITY REVIEW
-> PACKAGE VALIDATION
-> RELEASE APPROVAL
-> DISTRIBUTION

[MANDATORY]
A mandatory release gate must not be knowingly bypassed without an authorized exception.

INTEGRITY AND DISTRIBUTION

[MANDATORY]
Stable releases may only be distributed through authorized mechanisms.

[RECOMMENDED]
Release artifacts should have cryptographic hashes.

[RECOMMENDED]
Important release artifacts should be digitally signed.

RELEASE RECORDS

A significant release should retain:

* Product version.
* Build identifier.
* Source revision.
* Build configuration.
* Release date.
* Release channel.
* Test results.
* Security results.
* Package identifier.

FAILED RELEASES

[MANDATORY]
A failed release must not be represented as a successful stable version.

If a release causes a serious problem, distribution may be suspended, the affected version must remain identifiable, and a corrected release should be produced where appropriate.

[MANDATORY]
The historical record of a withdrawn release must not simply be erased.

EMERGENCY RELEASES

Emergency releases may be necessary for serious security or stability problems.

[MANDATORY]
Emergency handling must still preserve release identification and traceability.

[MANDATORY]
Security-critical fixes must receive appropriate validation even when the normal process is accelerated.

REPRODUCIBILITY

[RECOMMENDED]
Important releases should preserve enough information to recreate the build environment, including compiler, SDK, dependency, source, configuration, and shader-tool versions where relevant.

BUILD SECRETS

[MANDATORY]
Build credentials and other secrets must be protected.

[MANDATORY]
Build logs must not intentionally expose secrets.

RELEASE SECURITY

[MANDATORY]
Release artifacts must be protected against unauthorized modification to the extent reasonably possible.

[MANDATORY]
Only authorized people or systems may publish stable releases.

RELEASE DOCUMENTATION

Significant releases should have release notes, version information, known issues, and relevant security or installation information.

[RECOMMENDED]
Public release information should focus on changes relevant to Users rather than unnecessary internal implementation details.

MAINTENANCE

This process should be reviewed when the compiler, graphics stack, major dependencies, packaging system, distribution system, or security requirements materially change.
