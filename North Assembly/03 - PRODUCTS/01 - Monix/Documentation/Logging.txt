PURPOSE

The Monix logging system exists to make the application understandable when something happens, especially when something goes wrong. It provides operational visibility, diagnostics, security-event visibility, monitoring context, debugging information, and evidence for investigating failures.

LOGGING PRINCIPLES

[MANDATORY]
Logs must truthfully describe the events they represent.

[MANDATORY]
Severity must reflect the real importance of an event.

[MANDATORY]
Required diagnostic context must not be intentionally discarded.

[MANDATORY]
Secrets and protected information must be handled safely.

[MANDATORY]
Logging must not create uncontrolled resource consumption.

[RECOMMENDED]
Events should use a consistent structure across Monix subsystems.

SEVERITY

Monix uses the following principal severities:

INFO
Normal operational information.

WARNING
An unexpected or potentially problematic condition that does not necessarily stop operation.

ERROR
An operation failed or produced an invalid result.

CRITICAL
A severe failure affecting essential functionality, security, data integrity, or system stability.

KERNEL
A high-priority system-level event that requires the strongest diagnostic visibility within Monix's internal logging model.

[MANDATORY]
Severity must not be inflated or reduced simply to make an event look more or less important.

EVENT SOURCES

Events may originate from:

* Application startup and shutdown.
* Configuration.
* Monitoring.
* Process analysis.
* Security systems.
* SCRAM.
* Rendering.
* Shader processing.
* Shader cache.
* Networking.
* Updates.
* User actions.
* Internal failures.

[MANDATORY]
The source or subsystem responsible for an important event should be identifiable where technically possible.

LOG STRUCTURE

A log entry may contain:

* Timestamp.
* Severity.
* Category or source.
* Human-readable message.
* Relevant context.
* Error information where applicable.
* Affected resource or subsystem.

Monix does not require artificial event identifiers merely to make logs look structured. Context and meaningful messages are more important than arbitrary IDs.

TIMESTAMPS

[MANDATORY]
Timestamps must represent the event time as accurately as the implementation allows.

[MANDATORY]
The logger must not intentionally assign a false timestamp to an event.

[RECOMMENDED]
A consistent time source should be used throughout the application.

CATEGORIES AND CONTEXT

Useful context may include the product version, build, subsystem, file or resource, shader, pass, process, configuration state, or error information.

[MANDATORY]
Context must not intentionally expose protected information.

SENSITIVE INFORMATION

Sensitive information may include passwords, API keys, authentication tokens, private keys, session credentials, personal data, and other confidential information.

[MANDATORY]
Secrets must not be intentionally written to ordinary logs.

[MANDATORY]
Personal data must only be logged when there is a legitimate purpose and lawful basis where required.

[RECOMMENDED]
Sensitive values should be redacted or masked when diagnostic context genuinely requires them.

RUNTIME BUFFER

Monix may keep recent events in memory through a bounded runtime buffer.

[MANDATORY]
The buffer must have a controlled capacity.

[MANDATORY]
Normal operation must not cause unbounded memory growth because of logging.

[PENDING]
Final buffer capacity and retention behavior.

PERSISTENT LOGGING

Monix may persist logs to files or another supported storage mechanism.

[PENDING]
Persistent log location.

[PENDING]
Maximum log size.

[PENDING]
Retention period.

[MANDATORY]
Persistent logs must have an appropriate size or retention limit.

LOG ROTATION

Where persistent logging is enabled, logs may be rotated according to size, age, restart, or manual action.

[PENDING]
Final rotation strategy.

LOGGING LEVELS

Runtime verbosity may eventually be configurable, but increased verbosity must not disable required security or critical-error reporting.

[RECOMMENDED]
Highly verbose diagnostic logging should normally be limited in stable production builds unless it is explicitly needed for diagnosis.

SECURITY LOGGING

Security events may include authentication failures, unauthorized-access attempts, detections, SCRAM activity, update-verification failures, integrity failures, and privileged-operation failures.

[MANDATORY]
Security events must be recorded accurately and protected from unauthorized modification or disclosure where appropriate.

SCRAM LOGGING

SCRAM may record activation requests, mode checks, validation, authorization, actions, failures, and completion.

[MANDATORY]
Logs must clearly distinguish TEST mode from REAL mode.

[MANDATORY]
A failed SCRAM action must never be logged as successful.

MONITORING LOGGING

Monitoring may log collector startup and failure, unavailable sensors, threshold events, recovery, and other relevant state changes.

[MANDATORY]
A missing measurement must remain distinguishable from a valid measurement and from a security detection.

RENDERING AND SHADER LOGGING

Rendering logs may cover initialization, device selection, resources, pipelines, shaders, swapchain events, and recovery.

Shader logs may cover source loading, presets, dependencies, compilation, validation, cache operations, and runtime failures.

[MANDATORY]
A rendering or shader failure must identify the relevant subsystem or stage where practical.

LOG OUTPUT

Monix may support in-memory events, console output, persistent files, diagnostic exports, and internal event streams.

[PENDING]
Final supported output destinations.

[MANDATORY]
The destination must respect the classification of the information being logged.

LOG EXPORT AND FILTERING

Monix may allow logs to be filtered by severity, source, category, time range, subsystem, or search terms, and may provide diagnostic exports.

[MANDATORY]
Filtering must not alter the meaning of the underlying event.

[MANDATORY]
Exported logs must not intentionally contain secrets.

[RECOMMENDED]
Exports should support appropriate filtering and redaction.

LOG DISPLAY

The LOG interface may use event streams, tables, timestamps, categories, severity indicators, search, and filters.

[MANDATORY]
Critical information must remain readable.

[MANDATORY]
Visual effects must not hide critical errors or warnings.

PERFORMANCE

Logging consumes CPU, memory, storage, and potentially I/O bandwidth.

[MANDATORY]
The logger must not create uncontrolled resource consumption during normal operation.

[RECOMMENDED]
High-frequency events should use buffering, batching, or rate limiting where appropriate.

LOGGING FAILURE

Logging can fail because of full storage, permission errors, corrupted files, resource exhaustion, or unexpected application state.

[MANDATORY]
A logging failure must not falsely report that an event was persisted when it was not.

[RECOMMENDED]
Monix should use an alternative diagnostic path where practical if the primary logging destination fails.

LOG INTEGRITY AND ACCESS

[MANDATORY]
Important log events must not be modified in a way that changes their meaning.

[MANDATORY]
Restricted or sensitive logs must only be accessible to authorized persons.

[PENDING]
Security-log integrity mechanism and retention requirements.

DIAGNOSTIC MODE

Monix may provide a diagnostic or verbose mode.

[MANDATORY]
Diagnostic mode must not disable mandatory security controls.

[PENDING]
Diagnostic-mode activation and scope.

CONCURRENCY

Multiple subsystems may write events at the same time.

[MANDATORY]
Concurrent logging must not corrupt events or introduce unsafe shared-state behavior.

TESTING

Logging tests should cover:

* Severity selection.
* Timestamps.
* Formatting.
* Context.
* Buffer limits.
* Persistent storage.
* Rotation.
* Failure handling.
* Filtering.
* Export.
* Sensitive-data protection.
* Concurrent logging.

[MANDATORY]
Tests must verify that known secrets are not unintentionally written to logs.
