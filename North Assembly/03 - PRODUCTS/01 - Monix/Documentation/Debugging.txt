PURPOSE

This document defines the practical debugging process for Monix: identifying a problem, reproducing it, isolating the cause, making a fix, and proving that the fix actually works.

A disappearing symptom is not enough to call a problem solved.

DEBUGGING PRINCIPLES

[MANDATORY]
A reported problem must not be considered resolved only because the visible symptom disappeared.

[MANDATORY]
Important fixes must be checked for side effects.

[MANDATORY]
Debugging must not intentionally place passwords, credentials, tokens, private keys, or other sensitive information into logs or test artifacts.

[RECOMMENDED]
Problems should be reproduced before changing the affected code where practical.

STANDARD FLOW

REPORT
-> REPRODUCE
-> ISOLATE
-> ANALYZE
-> FIX
-> TEST
-> VERIFY

[MANDATORY]
A claimed fix must include an appropriate verification step.

ISSUE INFORMATION

A useful debugging report should identify:

* What happened.
* What was expected.
* How it was triggered.
* Affected version or build.
* Relevant environment.
* Logs or other evidence.
* Whether the problem is reproducible.

[MANDATORY]
Critical issues must be escalated appropriately.

ENVIRONMENT

Relevant diagnostic information may include Monix version, build identifier, operating system, CPU, GPU, graphics driver, memory, display configuration, active configuration, shader version, and relevant dependencies.

[RECOMMENDED]
Environment information should be collected automatically where practical.

DEBUG LOGGING

Useful debugging events may come from initialization, configuration, hardware detection, monitoring, rendering, shaders, cache operations, security, errors, and warnings.

[MANDATORY]
Debug logs must not intentionally expose secrets.

[RECOMMENDED]
Logs should contain enough context to identify the affected subsystem without becoming unnecessarily noisy.

LOG SEVERITY

DEBUG — detailed diagnostic information.

INFO — normal operational information.

WARNING — an unexpected condition that does not necessarily stop operation.

ERROR — an operation failed or produced an invalid result.

CRITICAL — a severe failure affecting essential functionality, security, or stability.

[MANDATORY]
Severity must accurately describe the event.

DEBUG BUILDS

Monix may use Debug, Development, Testing, and Release configurations.

[MANDATORY]
Development-only functionality must not unintentionally remain enabled in a stable release when it creates a security, stability, or information-disclosure risk.

RENDERING DEBUGGING

Rendering problems may involve Vulkan initialization, device selection, swapchain handling, resources, synchronization, pipelines, shaders, render passes, Dynamic Rendering, or frame execution.

A useful investigation follows:

INITIALIZATION
-> RESOURCE CREATION
-> SHADER VALIDATION
-> PIPELINE CREATION
-> FRAME EXECUTION
-> OUTPUT

[MANDATORY]
The failing stage should be identified where reasonably possible.

SHADER DEBUGGING

Shader failures may originate in source code, includes, dependencies, parameters, compilation, SPIR-V generation, reflection, pipeline creation, runtime execution, or resource synchronization.

[MANDATORY]
Shader failures must be reported with relevant context when available.

[RECOMMENDED]
Shader investigations should identify the shader or preset, pass, stage, relevant dependency, and failure stage where possible.

MULTI-PASS AND CACHE DEBUGGING

For multi-pass rendering, debugging must consider pass order, resource inputs and outputs, synchronization, feedback resources, resource lifetime, and format compatibility.

[MANDATORY]
Resource flow between passes must be checked when diagnosing a multi-pass failure.

For shader-cache problems, investigate cache keys, dependencies, compiler information, stale data, corruption, and failed cache writes.

[MANDATORY]
A cache entry must not be trusted merely because it exists.

MONITORING DEBUGGING

Monitoring problems may involve missing, stale, incorrect, or incorrectly scaled values, unsupported sensors, sampling errors, or driver limitations.

[MANDATORY]
An unavailable measurement must be distinguished from an incorrect measurement.

PROCESS ANALYSIS

Process problems may involve enumeration, permissions, executable metadata, paths, resource usage, reputation, or heuristic classification.

[MANDATORY]
Permission denial must not automatically be treated as malicious behavior.

SECURITY DEBUGGING

Security investigations may involve detections, reputation, heuristics, alerts, process actions, SCRAM, update verification, and access controls.

[MANDATORY]
High-impact security behavior must be tested in controlled conditions.

SCRAM DEBUGGING

SCRAM has two distinct operating contexts:

TEST MODE
Used to validate logic without intentionally executing actions reserved for real operation.

REAL MODE
Used only with appropriate authorization and controlled conditions.

[MANDATORY]
TEST and REAL behavior must remain clearly distinguishable.

[MANDATORY]
Debugging must not accidentally trigger a real high-impact action.

CONFIGURATION DEBUGGING

Investigations may involve missing values, invalid values, corrupted files, migrations, unexpected defaults, or conflicting settings.

[MANDATORY]
The effective configuration must be identifiable during diagnosis.

MEMORY AND CONCURRENCY

Memory investigations may cover leaks, use-after-free, double release, invalid ownership, unbounded allocation, and fragmentation.

Concurrency investigations may cover data races, deadlocks, race conditions, synchronization errors, and resource-lifetime conflicts.

[MANDATORY]
Fixes for concurrency or memory problems must be tested under conditions capable of exercising the affected behavior where practical.

CRASHES AND HANGS

Crash investigations may require the crash location, call stack, exception type, thread state, logs, active configuration, recent changes, and reproduction conditions.

When Monix hangs, investigate the main thread, worker threads, rendering synchronization, file and network operations, locks, GPU waits, and possible infinite loops.

[RECOMMENDED]
Thread dumps or equivalent diagnostic information should be captured when available.

PERFORMANCE DEBUGGING

Performance investigations may cover CPU, memory, GPU, frame time, startup, shutdown, shader compilation, logging, and I/O.

[MANDATORY]
A suspected bottleneck should be measured rather than inferred from a secondary symptom alone.

EXTERNAL SERVICES

External-service failures may involve network connectivity, authentication, API responses, timeouts, rate limits, or provider outages.

[MANDATORY]
An external failure must not automatically be classified as a local Monix failure without appropriate evidence.

REGRESSION VERIFICATION

After a significant fix:

ORIGINAL FAILURE
-> FIX
-> ORIGINAL TEST
-> RELATED TESTS
-> REGRESSION CHECK

[MANDATORY]
The original defect must be tested again.

[RECOMMENDED]
Related functionality should also be tested when the change could affect it.

ROOT CAUSE

For important issues, the investigation should go beyond the visible symptom and identify the underlying cause where possible.

Potential causes include incorrect assumptions, invalid state transitions, resource-lifetime errors, synchronization problems, invalid input handling, configuration problems, dependency behavior, and platform differences.

[RECOMMENDED]
Critical incidents should receive a documented root-cause analysis.

TEMPORARY DEBUGGING CHANGES

[MANDATORY]
Temporary debugging code, instrumentation, bypasses, and test switches must be identifiable.

[MANDATORY]
They must not accidentally reach a stable release when they alter intended security or product behavior.

[RECOMMENDED]
Temporary changes should be removed when their purpose is complete.

PRODUCTION DATA

[MANDATORY]
Production personal data and sensitive information must not be used unnecessarily during debugging.

[RECOMMENDED]
Synthetic or anonymized data should be preferred.

BUG-FIX VALIDATION

A fix should demonstrate that:

* The original defect no longer occurs.
* Expected behavior still works.
* Related functionality remains operational.
* No new critical failure was introduced.

[MANDATORY]
A fix must not be called verified when the relevant validation has not been performed.
