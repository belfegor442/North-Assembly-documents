PURPOSE

The Monix interface exists to make system information, diagnostics, security state, and controls understandable without hiding important information behind the visual style.

UI OBJECTIVES

The interface should provide:

* Clear system information.
* Predictable navigation.
* Readable diagnostics.
* Clear system states.
* Distinguishable warnings and errors.
* Controlled access to high-impact actions.
* A consistent North Assembly visual identity.

PRIMARY NAVIGATION

The main structure is:

LOG
TASKS
USAGE
AI
SETTINGS

Additional views may be added as the product develops.

[MANDATORY]
A navigation item must lead to the functionality represented by its label.

[MANDATORY]
Unavailable functionality must not be presented as fully operational.

INFORMATION HIERARCHY

The recommended priority is:

1. Critical system or security state.
2. Errors and warnings.
3. Current system status.
4. Primary controls.
5. Detailed information.
6. Secondary information.

[MANDATORY]
Critical information must not be intentionally hidden behind non-essential effects or controls.

LOG VIEW

The LOG view displays application, monitoring, diagnostic, and security events.

It may include timestamps, severity, source, categories, messages, context, filters, search, and supported export controls.

[MANDATORY]
Severity must be visually distinguishable.

[MANDATORY]
The UI must not report an operation as successful when it failed.

[RECOMMENDED]
Important events should expose their source and severity without requiring the User to open unrelated screens.

TASKS VIEW

The TASKS view provides process information such as name, identifier, CPU and memory usage, GPU usage where available, status, executable path, and security classification where supported.

[MANDATORY]
Displayed values must correspond to available system data.

[MANDATORY]
Unavailable values must not be presented as valid measurements.

[MANDATORY]
Process actions require the appropriate authorization.

USAGE VIEW

The USAGE view provides a high-level view of CPU, RAM, GPU, temperature, storage, and network activity.

It may use numeric values, indicators, graphs, and historical information.

[MANDATORY]
Units must be clear.

[MANDATORY]
Displayed state must match the current available telemetry.

AI VIEW

The AI view provides AI-assisted features where implemented, such as diagnostics, log analysis, monitoring interpretation, troubleshooting, and configuration suggestions.

[MANDATORY]
AI-generated information must remain distinguishable from measured system information.

[MANDATORY]
AI recommendations must not bypass normal authorization or validation.

[RECOMMENDED]
AI-generated responses should be clearly identified as such.

SETTINGS VIEW

Settings may include general, appearance, monitoring, logging, rendering, shaders, security, updates, AI, and diagnostics.

[MANDATORY]
Settings must validate values before applying them when invalid values could cause unsafe or unstable behavior.

[MANDATORY]
Security-critical settings must not be presented as ordinary cosmetic options when they have significant operational effects.

STATUS INDICATORS

Monix may represent states such as:

* Normal.
* Information.
* Warning.
* Error.
* Critical.
* Unavailable.
* Disabled.
* Loading.
* Processing.
* Stale.

[MANDATORY]
A status indicator must accurately represent its associated state.

[MANDATORY]
The meaning of a status must remain consistent throughout the application.

COLOR AND VISUAL SIGNALS

Color may communicate severity, status, selection, availability, and interaction state.

[MANDATORY]
Critical information must not rely exclusively on color.

[RECOMMENDED]
Important color-based states should also use labels, symbols, or another clear visual signal.

TYPOGRAPHY

Monix may use a distinctive typography system consistent with North Assembly's visual identity.

[PENDING]
Final primary and secondary fonts.

[MANDATORY]
Critical diagnostic text must remain readable on supported displays.

CRT / VHS VISUAL SYSTEM

Monix may use CRT- and VHS-inspired presentation, including scanlines, curvature, bloom, noise, distortion, ghosting, color effects, bezel effects, and shader-based presentation.

[MANDATORY]
Visual effects must not make critical information unreadable.

[MANDATORY]
Visual effects must not alter the meaning of telemetry, logs, or security results.

[RECOMMENDED]
Expensive effects should have a reduced or configurable mode where practical.

RENDERING FAILURE

[MANDATORY]
A failed visual effect or shader must not be presented as active.

[RECOMMENDED]
Monix should fall back to a valid rendering path where practical.

NAVIGATION AND CONTROLS

Navigation must remain predictable.

[MANDATORY]
Navigation must not unintentionally execute a high-impact operation.

Controls must behave consistently with their labels.

[MANDATORY]
High-impact controls must be distinguishable from ordinary controls.

[RECOMMENDED]
Actions with significant consequences should require an additional confirmation where accidental activation is reasonably possible.

DESTRUCTIVE ACTIONS

High-impact actions may include process termination, security changes, configuration reset, deletion, or emergency-response operations.

[MANDATORY]
The User must be able to understand the nature of a high-impact action before execution where reasonably possible.

[MANDATORY]
The interface must not describe a destructive action as harmless.

SCRAM INTERFACE

The UI should show whether SCRAM is available, its current mode, trigger state, authorization state, action state, and result.

[MANDATORY]
TEST and REAL modes must be visually distinct.

[MANDATORY]
The UI must not display a false active state.

[MANDATORY]
A failed SCRAM operation must not be represented as successful.

CONFIRMATIONS

[MANDATORY]
A confirmation prompt must describe the action that will actually be performed.

[MANDATORY]
Confirmation must not be shown as if an action were still pending after it has already occurred.

[RECOMMENDED]
The target of a high-impact action should be identified when doing so improves safety.

ERROR PRESENTATION

An error should communicate what failed, the relevant subsystem or category, its severity, and an available next step when one exists.

[MANDATORY]
The UI must not claim recovery when recovery did not occur.

[RECOMMENDED]
Technical diagnostic details should be available without overwhelming ordinary Users.

LOADING AND EMPTY STATES

Long-running operations may display loading, processing, compiling, updating, or recovering states.

[MANDATORY]
The UI must distinguish an operation that is still running from one that has failed.

Empty states may mean that no data exists, no process was found, a sensor is unavailable, or a feature is disabled.

[MANDATORY]
An empty state must not be called an error unless an actual error occurred.

UNAVAILABLE DATA

The interface may use labels such as N/A, Unavailable, Unsupported, Error, or Stale.

[MANDATORY]
Unavailable measurements must not be replaced with fabricated numbers.

LIVE DATA

Views showing live data may refresh periodically.

[MANDATORY]
The UI must not imply that a value is current when it is known to be stale.

[RECOMMENDED]
Important live data should expose a last-update indication where practical.

RESPONSIVENESS

Background work may include shader compilation, cache processing, monitoring, diagnostics, network requests, and large log processing.

[MANDATORY]
Long-running work must not unnecessarily block critical UI functionality.

PERFORMANCE

UI performance can be affected by large logs, process lists, graphs, shader effects, monitoring frequency, and data processing.

[MANDATORY]
The UI must not intentionally create uncontrolled resource consumption.

[RECOMMENDED]
Large datasets should use filtering, virtualization, pagination, or another appropriate strategy where practical.

ACCESSIBILITY

[MANDATORY]
Critical information must remain distinguishable without relying only on color.

[MANDATORY]
Interactive controls must remain understandable through their labels or equivalent descriptions where applicable.

[RECOMMENDED]
The interface should support readable scaling and reasonable contrast.

RESPONSIVE LAYOUT

[MANDATORY]
Essential controls and critical information must remain usable within supported window sizes.

[PENDING]
Minimum supported window size.

DISPLAY SCALING

[MANDATORY]
Text and critical controls must remain usable on supported high-DPI and scaled displays.

KEYBOARD AND POINTER INPUT

[PENDING]
Final keyboard shortcuts.

[MANDATORY]
Shortcuts must not unintentionally trigger high-impact actions without appropriate safeguards.

Controls may expose normal, hover, focused, pressed, and disabled states.

[MANDATORY]
A disabled control must not appear to have successfully executed its action.

NOTIFICATIONS

Notifications may communicate errors, security events, updates, long-running operations, and important system conditions.

[MANDATORY]
Notifications must accurately describe their underlying event.

[RECOMMENDED]
Critical notifications should remain visible long enough to be understood.

UI AND LOGGING

Important UI actions may produce log events, including configuration changes, security actions, SCRAM operations, and other meaningful state transitions.

[MANDATORY]
UI logging must follow the Monix Logging Documentation and must not expose secrets.

UI AND SECURITY

[MANDATORY]
The interface must not provide a way around backend authorization, validation, or security controls.

[MANDATORY]
Hiding a control is not a substitute for enforcing its permission requirements in the underlying subsystem.

UI STATES MUST BE REAL

[MANDATORY]
The interface must represent actual application state rather than an assumed or desired state.

Examples:

A shader that failed to compile must not appear active.

A measurement that is unavailable must not appear as zero merely because zero is easier to display.

An update that failed must not appear installed.

A security action that was rejected must not appear completed.

TESTING

UI testing should cover:

* Navigation.
* Data presentation.
* Status indicators.
* Errors.
* Loading states.
* Unavailable data.
* Settings.
* High-impact confirmations.
* SCRAM state display.
* Scaling.
* Keyboard and pointer input.
* Rendering failures.
* Performance.
* Accessibility.

[MANDATORY]
UI tests must verify that the displayed state matches the underlying application state.
