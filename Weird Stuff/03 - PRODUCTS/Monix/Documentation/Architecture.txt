PURPOSE

This document describes how Monix is organized internally: the main layers, subsystem boundaries, data flow, and the rules that keep one part of the application from bypassing another.

The architecture can change during development. When a change materially affects responsibilities or boundaries, this document should be updated rather than leaving the architecture defined only in source code or discussion.

ARCHITECTURAL PRINCIPLES

Monix is built around clear responsibilities, explicit boundaries, controlled access to privileged operations, safe failure handling, testability, maintainability, traceability, and security by design.

[MANDATORY]
A subsystem must not intentionally bypass another subsystem's responsibilities or security boundaries without authorization.

HIGH-LEVEL STRUCTURE

USER
-> PRESENTATION
-> APPLICATION
-> DOMAIN
-> INFRASTRUCTURE
-> PLATFORM / OS
-> HARDWARE

Graphics follow a related path:

UI / RENDERING
-> SHADER SYSTEM
-> VULKAN
-> GPU

PRESENTATION

The Presentation layer contains the user-facing interface, including LOG, TASKS, USAGE, AI, SETTINGS, status displays, tables, event streams, and visual effects.

[MANDATORY]
Presentation code must not perform privileged system operations directly when the operation belongs behind an application, domain, infrastructure, or platform boundary.

[MANDATORY]
Information shown to the User must accurately reflect the state reported by the underlying systems.

APPLICATION

The Application layer coordinates commands, user actions, workflows, feature interaction, and state transitions.

[MANDATORY]
Application logic must not skip required validation, authorization, or security checks.

DOMAIN

The Domain layer contains Monix-specific concepts and rules. These may include processes, metrics, events, alerts, security findings, snapshots, configuration, shader resources, and product state.

[MANDATORY]
Domain logic should not depend on unnecessary platform-specific details where a suitable abstraction is available.

INFRASTRUCTURE

Infrastructure provides the technical services used by the rest of Monix. This includes logging, storage, configuration persistence, shader caching, metrics collection, process enumeration, networking, external services, and update infrastructure.

[MANDATORY]
Infrastructure components must enforce the security and access requirements of the resources they manage.

PLATFORM

The Platform layer connects Monix to the operating system and available hardware. It may provide process, memory, CPU, GPU, storage, network, temperature, permission, and other native interfaces.

[MANDATORY]
Platform-specific failures must be handled safely.

[RECOMMENDED]
Platform-specific functionality should be isolated behind defined interfaces where practical.

HARDWARE

Monix may obtain information from the CPU, RAM, GPU, storage, network interfaces, temperature sensors, and other available hardware resources.

[MANDATORY]
Unavailable or unsupported hardware information must never be represented as verified telemetry.

EVENT FLOW

A typical monitoring event follows this general path:

SYSTEM SOURCE
-> PLATFORM ADAPTER
-> INFRASTRUCTURE
-> DOMAIN EVENT
-> APPLICATION PROCESSING
-> PRESENTATION
-> USER

[MANDATORY]
Important events should retain enough context to determine their origin and meaning where technically possible.

LOGGING

Logging is a cross-cutting subsystem. It may receive events from presentation, application, domain, infrastructure, platform, rendering, shaders, and security components.

[MANDATORY]
Logs must not intentionally expose passwords, private keys, tokens, or other secrets.

[MANDATORY]
Important errors must not be silently converted into successful results or discarded without an appropriate reason.

MONITORING

The monitoring path is conceptually:

SYSTEM
-> COLLECTOR
-> NORMALIZATION
-> VALIDATION
-> METRICS MODEL
-> PRESENTATION

[MANDATORY]
Invalid or unavailable measurements must be identified before they are presented as valid telemetry.

PROCESS ANALYSIS

Process analysis may combine process enumeration, executable metadata, resource usage, reputation information, heuristic analysis, and security findings.

PROCESS
-> COLLECTION
-> ANALYSIS
-> CLASSIFICATION
-> RESULT
-> USER INTERFACE

[MANDATORY]
Heuristic conclusions must remain distinguishable from verified facts.

SECURITY ARCHITECTURE

Security-sensitive functionality may include process analysis, reputation checks, detections, alerts, SCRAM, access controls, and security logging.

[MANDATORY]
Security-sensitive operations should remain isolated from unrelated functionality wherever practical.

[MANDATORY]
User-visible information must not be treated as automatically trustworthy merely because it originated inside Monix.

SCRAM

SCRAM is the emergency-response subsystem for defined protective actions.

TRIGGER
-> VALIDATION
-> MODE CHECK
-> AUTHORIZATION
-> ACTION
-> RESULT
-> LOG

[MANDATORY]
TEST mode must not intentionally execute actions reserved for REAL mode.

[MANDATORY]
REAL mode must verify the required authorization and validation conditions before high-impact operations.

SNAPSHOTS

Snapshots may combine monitoring, process, configuration, event, application-state, and security information.

SUBSYSTEMS
-> STATE COLLECTION
-> NORMALIZATION
-> SNAPSHOT
-> STORAGE

[MANDATORY]
A snapshot must accurately represent the information that was actually captured.

CONFIGURATION

Configuration may control the interface, logging, monitoring, rendering, security, performance, shaders, and other product settings.

USER INPUT
-> VALIDATION
-> CONFIGURATION MODEL
-> PERSISTENCE
-> RUNTIME

[MANDATORY]
Invalid configuration values must not be applied when they could cause unsafe or undefined behavior.

RENDERING

Monix uses a Vulkan-oriented rendering architecture. The general rendering path is:

APPLICATION
-> RENDERING SYSTEM
-> RENDER GRAPH / PASS EXECUTION
-> SHADER PIPELINE
-> VULKAN
-> GPU

The renderer may use Dynamic Rendering, SPIR-V, Slang, shader presets, multi-pass rendering, runtime resource management, and shader caching.

SHADER SYSTEM

The shader subsystem handles loading, preset parsing, dependency resolution, compilation, SPIR-V generation, pipeline creation, runtime resources, and caching.

.SLANG / .SLANGP
-> PARSER
-> DEPENDENCY RESOLUTION
-> COMPILATION
-> SPIR-V
-> PIPELINE
-> VULKAN
-> GPU

[MANDATORY]
Invalid shader resources must not be treated as valid runtime resources.

[MANDATORY]
Shader failures must be reported accurately.

MULTI-PASS SHADERS

A multi-pass pipeline may contain shader programs, input and output resources, uniforms, dependencies, feedback resources, and execution order.

PASS 1
-> PASS 2
-> PASS 3
-> ...
-> FINAL OUTPUT

[MANDATORY]
Pass dependencies must be resolved before execution.

[MANDATORY]
Resources must only be accessed within their valid lifetime and declared usage.

SHADER FEEDBACK

Feedback resources may carry previous-frame or previous-pass information.

[MANDATORY]
Feedback resources must be synchronized according to the requirements of the graphics API and must not be treated as initialized before they are actually initialized.

SHADER CACHE

The shader cache may use source contents, shader stage, language, compiler version, dependencies, and relevant configuration as part of cache identity.

SOURCE
-> KEY GENERATION
-> CACHE LOOKUP
-> VALIDATE / LOAD
or
-> COMPILE
-> STORE

[MANDATORY]
Relevant source, dependency, compiler, or compatibility changes must invalidate affected cache entries.

[MANDATORY]
Corrupted or incompatible cache data must not be blindly trusted.

ERROR HANDLING

Errors generally move upward through the architecture:

LOW-LEVEL ERROR
-> ADAPTER
-> INFRASTRUCTURE / DOMAIN
-> APPLICATION
-> PRESENTATION

[MANDATORY]
Errors must not be silently converted into successful results.

[RECOMMENDED]
User-facing errors should remain understandable while authorized internal logs retain the information needed for diagnosis.

DEPENDENCY DIRECTION

The preferred direction is:

PRESENTATION
-> APPLICATION
-> DOMAIN
-> INFRASTRUCTURE
-> PLATFORM

Graphics infrastructure additionally communicates with the graphics API and driver stack.

[MANDATORY]
Lower-level implementation details must not unnecessarily leak into high-level interfaces.

THREADING AND CONCURRENCY

Monix may perform monitoring, logging, rendering, shader compilation, cache operations, process analysis, and UI work concurrently.

[MANDATORY]
Shared resources must be synchronized appropriately.

[MANDATORY]
Concurrent operations must not intentionally introduce data races, undefined access, or corruption of persistent state.

[RECOMMENDED]
Expensive or long-running work should be kept away from the main UI execution path where practical.

RESOURCE MANAGEMENT

Monix manages resources such as memory, files, GPU and Vulkan objects, threads, processes, and network resources.

[MANDATORY]
Owned resources must be released appropriately.

[MANDATORY]
Failed resource initialization must not be reported as successful initialization.

SECURITY BOUNDARIES

Security boundaries may exist between the UI, monitoring, process analysis, security systems, system APIs, rendering, update mechanisms, and external services.

[MANDATORY]
Crossing a security boundary requires the permissions and validation appropriate to the operation.

EXTERNAL SERVICES

External services may eventually support areas such as update distribution, AI, analytics, authentication, or remote infrastructure.

[PENDING]
Approved external services and their final integration boundaries.

ARCHITECTURAL CHANGE CONTROL

[MANDATORY]
Changes that materially alter subsystem responsibilities, privileged access, data flow, or security boundaries must be reflected in the controlled architecture documentation.

[RECOMMENDED]
Large architectural changes should be reviewed before implementation is treated as final.
