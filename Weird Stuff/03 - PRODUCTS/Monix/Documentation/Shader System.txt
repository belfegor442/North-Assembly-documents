PURPOSE

The Monix shader system turns shader resources into executable GPU rendering pipelines. This document covers formats, presets, dependencies, compilation, validation, Vulkan pipeline creation, multi-pass rendering, feedback resources, caching, hot reload, failure handling, and security.

GENERAL FLOW

SHADER SOURCE
-> PRESET / CONFIGURATION
-> DEPENDENCY RESOLUTION
-> VALIDATION
-> COMPILATION
-> SPIR-V
-> REFLECTION
-> PIPELINE CREATION
-> VULKAN
-> GPU

SUPPORTED RESOURCES

Monix may process:

* .slang source.
* .slangp presets.
* SPIR-V artifacts.

[MANDATORY]
A file is not a valid shader merely because its extension is recognized.

SLANG SOURCE

Shader source may define vertex, fragment, and supported compute stages, resources, uniforms, samplers, textures, helper functions, includes, and other dependencies.

[MANDATORY]
Source must be validated and compiled before it is used as a runtime pipeline component.

SLANG PRESETS

Presets may describe shader passes, paths, parameters, resources, outputs, dependencies, and feedback behavior.

Typical processing is:

LOAD
-> PARSE
-> RESOLVE REFERENCES
-> RESOLVE PATHS
-> RESOLVE PARAMETERS
-> BUILD PASSES
-> VALIDATE

DEPENDENCIES

Dependencies may include include files, shared shader functions, presets, configuration, and other shader resources.

[MANDATORY]
Relevant dependencies must be resolved before the affected resource is considered valid.

[MANDATORY]
Missing dependencies must produce a clear failure rather than silently selecting an unrelated resource.

PATH RESOLUTION

[MANDATORY]
Resolved paths must refer to the intended resource.

[MANDATORY]
Untrusted paths must not bypass applicable filesystem or application security boundaries.

[RECOMMENDED]
Paths should be normalized before use.

VALIDATION

Validation may occur at the source, preset, dependency, compilation, SPIR-V, reflection, and runtime-pipeline stages.

[MANDATORY]
A validation failure is a failure. Invalid shader resources must not be silently accepted.

COMPILATION

The compiler transforms supported shader source into a representation suitable for the Vulkan pipeline.

SOURCE
-> COMPILER
-> SPIR-V
-> VALIDATION
-> RUNTIME

[MANDATORY]
Compiler failures must propagate accurately.

[MANDATORY]
Failed compilation must never be reported as successful compilation.

[RECOMMENDED]
Compiler diagnostics should remain available for troubleshooting.

COMPILER COMPATIBILITY

Shader compilation depends on the compiler implementation and version.

[MANDATORY]
Compiler version must be considered when deciding whether cached shader data remains compatible.

SPIR-V

[MANDATORY]
SPIR-V loaded or generated by Monix must be validated to the level required by the implementation before runtime use.

[MANDATORY]
Invalid SPIR-V must not become a valid shader module.

REFLECTION

Reflection may identify uniform buffers, storage buffers, textures, samplers, push constants, bindings, and shader stages.

[MANDATORY]
Runtime resource bindings must match the shader's actual declared resources.

PIPELINE CREATION

Validated shader modules may be used to create Vulkan pipelines.

SPIR-V MODULES
-> REFLECTION
-> PIPELINE LAYOUT
-> GRAPHICS PIPELINE
-> RUNTIME

[MANDATORY]
Pipeline creation failure must not leave the pipeline marked as usable.

[MANDATORY]
Pipeline and shader resources must be released correctly when they are no longer required.

MULTI-PASS PIPELINES

A preset may describe several rendering passes. A pass may define its shader, inputs, outputs, parameters, bindings, feedback resources, and execution order.

PASS 1
-> PASS 2
-> PASS 3
-> ...
-> FINAL OUTPUT

[MANDATORY]
Pass dependencies must be resolved before execution.

[MANDATORY]
Resources must be synchronized according to their actual usage.

RENDER TARGETS

Passes may use intermediate textures, off-screen targets, swapchain-related outputs, and other valid Vulkan resources.

[MANDATORY]
A pass must not write to an invalid, unavailable, or incompatible target.

EXTERNAL TEXTURES

External textures may be supplied by the renderer or another Monix subsystem.

[MANDATORY]
External resources must be validated before being bound to a shader.

FEEDBACK RESOURCES

Feedback allows a pass to use data generated by an earlier pass or frame.

PREVIOUS FRAME
-> FEEDBACK RESOURCE
-> CURRENT SHADER
-> NEW OUTPUT
-> NEXT FRAME

[MANDATORY]
Feedback resources must follow Vulkan synchronization requirements.

[MANDATORY]
Uninitialized feedback data must not be treated as valid.

PARAMETERS

Shader parameters may come from uniforms, push constants, descriptor resources, presets, or runtime configuration.

[MANDATORY]
Values must match the expected type and valid range where such validation is possible.

[MANDATORY]
Invalid parameters must not intentionally create undefined behavior.

SHADER CACHE

The cache reduces repeated compilation. Cache identity may depend on source, stage, language, compiler version, dependencies, and relevant compilation configuration.

RESOURCE
-> KEY GENERATION
-> CACHE LOOKUP
-> VALIDATE / LOAD
or
-> COMPILE
-> STORE

[MANDATORY]
Relevant source, dependency, compiler, or compatibility changes must invalidate affected cache entries.

[MANDATORY]
Corrupted or incompatible cache entries must not be trusted.

[RECOMMENDED]
Cache writes should be atomic where practical.

CACHE EVICTION

The cache may use size, age, or LRU-based eviction.

[PENDING]
Final cache-size and eviction policy.

HOT RELOAD

Monix may support runtime shader reloads.

FILE CHANGE
-> DETECT
-> RELOAD
-> VALIDATE
-> COMPILE
-> CREATE PIPELINE
-> ACTIVATE

[MANDATORY]
A failed reload must not replace a valid active pipeline with an invalid one.

[RECOMMENDED]
When possible, the previous valid pipeline should remain active after a failed reload.

TRANSACTIONAL SHADER STATE

A shader change should behave like a candidate state that is validated before becoming active.

CURRENT VALID STATE
-> CANDIDATE STATE
-> VALIDATION
-> COMMIT

If validation fails, the current valid state remains active where safe rollback is possible.

ERROR HANDLING

Shader failures may originate in file access, parsing, dependency resolution, compilation, SPIR-V validation, reflection, resource creation, pipeline creation, or runtime execution.

[MANDATORY]
The source of a failure must not be intentionally misrepresented.

[RECOMMENDED]
Errors should identify the relevant shader, pass, stage, or dependency where possible.

FAILURE ISOLATION

[MANDATORY]
A failure in an optional shader or pass must not unnecessarily terminate unrelated Monix functionality.

Possible fallback behavior may include a previous valid shader, a default shader, a disabled effect, or a reduced rendering path, depending on the implementation.

SECURITY

Shaders are executable GPU programs and may come from trusted or untrusted sources.

[MANDATORY]
Shader processing must not intentionally bypass application, operating-system, or graphics-driver security boundaries.

[MANDATORY]
A shader is not trusted merely because it was found in a recognized directory.

THIRD-PARTY SHADERS

[MANDATORY]
Third-party shader resources must comply with their licenses.

[MANDATORY]
Required attribution and license information must be preserved.

TESTING

The shader system should be tested for:

* Valid and invalid source.
* Missing dependencies.
* Invalid presets.
* Reference failures.
* Compilation errors.
* Reflection mismatches.
* Pipeline failures.
* Cache corruption and invalidation.
* Hot reload failures.
* Multi-pass failures.
* Feedback resources.
* Unsupported resources.

[MANDATORY]
Critical shader functionality must pass applicable tests before stable release.

PERFORMANCE

Shader performance depends on compilation cost, cache behavior, number of passes, resource sizes, synchronization, and GPU capabilities.

[MANDATORY]
Performance optimizations must not bypass validation or synchronization requirements.

[RECOMMENDED]
Expensive compilation should run asynchronously where practical.
